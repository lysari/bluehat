# Bluehat Roadmap

Updated 2026-11-04. Each phase ships as a working app; later phases depend on the earlier ones being done.

## Phase 0: Foundation (done)

- [x] Menu bar app with a Scan button (`NSStatusItem` with a floating SwiftUI panel)
- [x] Rules come only from `lysari/bluehat-rules`, Ed25519-signed, verified against the built-in public key; since 2026-11-02 they ship inside the app and update only after review in Settings › Rules
- [x] Data-only rules over 8 built-in check types; no redirects, 2 MB cap, rollback guard, verified offline cache
- [x] `bluehat-sign` CLI with the private key in the login Keychain
- [x] 22 starter rules, 20 tests, Devbox commands

## Phase 1: Professional UI (done)

- [x] Status card with states for ready, scanning, safe, issues and failure
- [x] Scan ring: one segment per check area, live progress, radar sweep, status glow (respects Reduce Motion)
- [x] 3D shield emblem with hover tilt and scanning float, in the ring and the header
- [x] Findings card sorted by severity, with fix guidance and Show in Finder
- [x] "What Bluehat checks" grid with a pass/fail state per area
- [x] The grid shows which check is running, with a spinner and a tinted row (static with Reduce Motion), and a Disk walk row during a Deep Scan with its live count
- [x] Click any check for a popover: what it looks for, where, what a finding means and what it reads or sends, written from the check's code
- [x] Signed-rules footer, More menu, light and dark mode, concentric corners
- [x] App icon (`.icns`): 3D shield in the scan ring on a navy tile, generated by `devbox run icon`
- [x] Menu bar glyph: template Bluehat shield with a mark per state, scan progress ring and the issue count
- [x] Finding detail view: what was found, why it matters, how to fix, source links, ignore
- [x] First-run welcome explaining the Files & Folders prompt and the signed rules, with schedule and login toggles
- [x] Settings window (General, Schedule, Ignored, About)

## Phase 2: Daily use (done)

- [x] Launch at login (`SMAppService`), switch in Settings
- [x] `devbox run install` copies the app to `/Applications`
- [x] Scheduled background scans (off, 1, 6, 12, 24 h) with a notification only for new issues
- [x] Custom scan in Settings › Schedule: one normal scan at a chosen date and time, run after wake or at the next launch if missed, then the schedule turns Off
- [x] Ignore list per exact finding, stored locally, reviewable in Settings, count always shown
- [x] Scan history: last 30 scans with what changed between them
- [x] Findings list layout in Settings › General: Normal (flat, by severity) or Grouped (by check area, most severe area first)
- [x] Collapsible finding groups, all expanded again on each new scan result, staying lazy for thousands of findings
- [x] Group actions in a ⋯ menu: Copy Fix Steps, Ignore All after a warning, and Move All to Trash for copies that already offer Move to Trash, refusing system locations and reporting every failure; no Fix All, on purpose
- [x] Settings › Ignored grouped the same way, collapsible, with Remove All per group
- [x] Findings and Not Scanned tabs: everything a scan knows it didn't check, by reason, with your home folder first, in place of a long orange paragraph; a calm line in the status card opens it, and orange stays for what you must act on
- [x] Search as you type and a filter menu on both tabs, ignoring case and diacritics; a filter never changes status, resets with each scan, and group actions act only on what is shown and say so
- [x] Keep panel on top switch in Settings › General: on by default; off lets other windows cover the panel, and the shield brings it back to the front
- [x] Adjustable scan limits in Settings › Limits: every limit on what a scan reads, counts, waits for or keeps, with a hard range, reset per row and for all, validated on load, and named in the notice of any scan that used a changed value; trust chain limits stay fixed
- [x] A crafted JSON file can't stop a scan: lockfiles, package manifests and browser extension files nested deep enough to crash the parser are refused before parsing and listed under Not Scanned, at a fixed bound no limit can raise
- [x] Warn when the verified rules expire within 30 days (signed `expires`; blocks a freeze attack, where updates are silently held back)

## Phase 3: Detection depth (in progress)

New check types (each needs an app update; rules then use them):

- [x] `launchItemSignature`: launch items whose program is unsigned, ad-hoc signed or tampered (all architectures)
- [x] `appSignature`: apps in Applications and Downloads that are unsigned, ad-hoc signed or changed after signing
- [x] Older apps skip rules with unknown check types instead of rejecting the rulebook
- [x] `notarization`: Developer ID apps that aren't notarized; checked offline from the stapled or locally known ticket (40 apps in 0.3 s), Gatekeeper's online verdict (`spctl`) only for the rest, at most 5 per scan, cached per app path and code hash
- [x] `browserExtension`: Chrome, Brave, Edge, Arc, Chromium, Vivaldi and Firefox extensions; flags extensions outside official stores, cookie access on every site, debugger and proxy permissions
- [x] Known-bad extension IDs from published compromise reports, matched by ID with `browserExtension` patterns: Cyberhaven campaign (Secure Annex, 22 IDs; 10 more that were fixed since at low severity), GitLab's CSP-stripping cluster (16), RedDirection (18) and ShadyPanda (159) from Koi
- [ ] Extension version in the `browserExtension` descriptor, so hijacked extensions that were fixed since (and one-release hijacks such as a single bad wallet update) are flagged only in their bad versions
- [x] `profile`: user configuration profiles, flagging proxy, DNS, root certificate, content filter and browser policy payloads (computer-wide profiles need root)
- [x] `systemExtension`: system extensions not from a known team ID and loaded third-party kernel extensions not from a known bundle ID
- [x] `softwareVersion`: vulnerable developer tool versions (Node.js, PHP, Python, OpenSSL, Git, Ruby), rules generated from OSV.dev
- [x] `npmPackage`: malicious npm package versions from the signed feed, in project lockfiles and global `node_modules`
- [x] `projectFile`: code injected into npm project config files and install scripts (rules pick file names and patterns; the app picks the projects)
- [x] `sshKey`: every key in `~/.ssh/authorized_keys` with its fingerprint; ignore known keys so only new ones return
- [x] `outbound`: open TCP and UDP connections of every process (`netstat -anlv`, no root) to listed addresses, ranges or ports (C2 beacons), with state and process name; loopback and link-local skipped, no DNS lookups
- [x] `xprotect`: XProtect definitions older than the rules' minimum version
- [x] Deep Scan: started by the user from the panel, runs the normal scan with all its limits, then walks the startup disk one file at a time at background priority and opens only `package.json`, `*.config.*` and lockfile names, shows progress, can be cancelled without recording a result, skips the folders excluded in Settings › General, and is marked in scan history
- [x] Deep Scan exclude patterns in Settings › General: `.gitignore`-style globs beside the folder picker, matched case-insensitively by a hand-written matcher with no regular expressions or combinatorial backtracking, with whole-disk patterns refused and every pattern named in the scan's notice
- [x] Deep Scan coverage in the Not Scanned tab: folders read, package files opened and folders that couldn't be read, counted during the walk with no extra disk access; excluded folders, cloud-only files and other volumes don't count as unreadable
- [x] Deep Scan opens `*.config.cts` and `*.config.mts` across the disk
- [x] Other volumes, `/dev` and external drives included, no longer count as Not Scanned: a Deep Scan stays on the startup disk by design, and the tab says so once in its summary
- [x] A launch item plist that can't be parsed, or whose top level isn't a dictionary, is listed under Not Scanned as Could not parse, with no finding
- [x] App signing and Launch signing validate with no network, giving up online certificate revocation lookups, whose answer never produced a finding
- [ ] `pythonPackage`: malicious PyPI package versions in project lockfiles (`requirements.txt`, `poetry.lock`, `uv.lock`, `Pipfile.lock`) and installed `site-packages`
- [ ] `cargoPackage`: malicious crates in project `Cargo.lock` files
- [ ] `goModule`: malicious Go modules in project `go.sum` files
- [ ] `bun.lock` support in `npmPackage`, which reads only `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock` and `pnpm-lock.yaml` today
- [ ] Install scripts and hidden code inside installed `node_modules` packages, which `projectFile` skips today, to catch a new malicious release before it reaches the feed
- [ ] `secretExposure`: plaintext tokens and keys in `.env` files, cloud and package manager credential files; names the file and the kind of secret, never stores or shows the value
- [ ] `bytePattern`: signed byte patterns matched in capped reads of files, so a rebuilt sample with a new SHA-256 is still found; rules stay data, with no rule language that can run code

Rule content:

- [x] Current stealer indicators from primary reports: AMOS backdoor (Trend Micro), CrashStealer (Jamf), ClickLock (RH-ISAC), Sapphire Sleet (Microsoft), ICMacOS (SOCRadar)
- [x] Behaviour rules: stealer upload/zip/fake password prompt/`curl | osascript`, stealer backdoor processes, Apple-named launch items outside /System
- [x] Indicators for Poseidon (Malwarebytes, NCSC), Banshee (Elastic, Check Point), Odyssey (Jamf, CYFIRMA) and SHub Reaper (SentinelOne, Moonlock): staging folders and backdoor files, upload and bot-loop processes, and a program-path rule for SHub's fake `GoogleUpdate.app` instead of its `com.google.keystone.agent.plist` name, which Google's real updater also uses. Odyssey's randomly named LaunchDaemon has no published fixed name or program, so the generic launch item rules cover it
- [x] SHA-256 hashes of current macOS malware samples: daily MalwareBazaar fingerprint feed (`feed.signed.json`), one critical rule per family, optional so a missing feed never blocks a scan
- [x] Current macOS C2 server addresses: daily ThreatFox `ip:port` IOCs of `osx.*` families (confidence 75+, last 30 days) in the signed feed, one `outbound` rule per family; no hand-written C2 rules, since published addresses go stale within days
- [x] `summary`, `remedy` and `references` fields per rule
- [ ] Malicious PyPI, crates.io and Go package versions from OSV.dev in the daily feed, once their check types exist
- [ ] Byte pattern rules for current stealer families, once `bytePattern` exists

## Phase 7: Real-time protection and system-wide visibility

The extensions and the helper need Developer ID signing from Phase 5, and the extensions also need Apple's approval for the Endpoint Security and Network Extension entitlements. Blocking changes the "Bluehat only reads" promise, so each blocking item is opt-in and the README's privacy section changes with it.

- [ ] Connection checks between scans, so a short-lived connection to a listed server isn't missed; still read-only, with no new entitlement
- [ ] Endpoint Security system extension: see programs as they start and block known malware before it runs
- [ ] Network Extension content filter: block connections to listed command-and-control servers instead of only reporting them
- [ ] Optional privileged helper with Full Disk Access, for computer-wide profiles and files a user-level scan can't read
